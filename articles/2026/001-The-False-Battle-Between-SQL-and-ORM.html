The False Battle Between SQL and ORM

For years, the ORM vs SQL debate has been framed as a war of tools. Some say ORMs are slow and hide the real power of the database. Others argue that a "well used" ORM solves every problem. Both approaches fail for the same reason: they start from a misunderstanding of what problem each one solves.

An ORM lives in memory. SQL is a language for communicating with persistent storage. They do not compete; they operate at different layers. SQL is designed to talk to disks, indexes, pages, execution plans, and data sets. The ORM exists to work with state in RAM, with live objects, identity, transactions, and consistency while the application is running. Confusing those roles is the origin of many bad designs.

When you write good SQL, you are optimizing the conversation with storage. You are saying: "bring me this data, filtered, aggregated, ordered, in the most efficient way possible." When you use an ORM, you are saying: "I want to work with this data as objects, with behavior, with semantics, with a clear lifecycle inside my application." The ORM does not replace SQL; it generates the SQL you do not want to write over and over, and it keeps a coherent state before persisting changes.

That is why, if you decide to work in an object-oriented paradigm, using structures like arrays of arrays starts to lose semantic sense. It is not just an aesthetic issue. It is a matter of mental model. It does not mean the same thing to write an array with data as to create an object with identity and behavior. An object is not just a container of values; it represents a domain entity with intent and lifecycle.

When you write something like:

$person = new Person();
$person->setName('John');

semantically you are saying much more than "I have data." You are saying that a person exists in your model, that it can be validated, modified, persisted, or discarded, and that its state can accumulate until you decide to commit a transaction. That idea of "prepare changes and commit at the end" is not an implementation detail: it is one of the main reasons ORMs exist, through concepts like unit of work and dirty checking.

The same happens when you access relationships. If you write:

$person->getNotes();

what you expect is not a raw array, but a collection of Note objects, built from the necessary tables, with the proper SQL running underneath. Whether the ORM executes joins, extra queries, or uses lazy loading is not an error in itself. The error is not understanding what SQL is being executed or when. The ORM should not be a black box, but there is nothing wrong with it doing its job.

Another point that is often missed is that an object does not have to correspond to a single table, nor does a table have to map one-to-one to a class. A domain object can be built from multiple tables, views, or aggregations. Solving that only with SQL can quickly become verbose and repetitive. Solving it only with objects, ignoring the database, can be inefficient. The value lies in knowing when to use each approach.

PostgreSQL also allows business rules to live in the database: complex constraints, triggers, functions, validations. That is perfectly valid and, in many cases, desirable. Not everything has to live in the application. But not everything should live in the database either. The right question is not "ORM or SQL?" but "where does this responsibility make the most sense to live, and what is the real cost of keeping it there?"

The underlying problem is not technical, it is conceptual. The ORM does not exist to avoid thinking about SQL, nor does SQL exist to replace the domain model. The ORM exists to solve the mismatch between objects and relations, to allow working with in-memory state coherently, and to generate reasonable SQL when there is no need to write it by hand. SQL exists to do what it does best: operate efficiently on persistent data.

Being a SQL lover does not force you to become a purist. Using an ORM does not force you to delegate everything to the framework. Mature engineering appears when the concepts are understood and used as convenient, without dogma. If an ORM "feels slow," many times it is not the ORM's fault, but a poor mental model of what problem is being solved and in which layer.

Understanding that changes the discussion completely. And, curiously, it makes ORM and SQL stop looking like enemies and become what they always were: complementary tools, each with a clear role inside a well-designed system.

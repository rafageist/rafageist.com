Don't use AI to rewrite the world

Important

Use AI to extend what already works

Why does generating everything from scratch tend to be the wrong level of abstraction? Artificial intelligence has accelerated software development in a remarkable way. Today there are tools capable of generating complete files, modules, and even entire applications in a matter of minutes. This capability has changed the way many teams work and has drastically reduced the time needed to write code.

However, this new speed is also creating a well-known problem: more and more teams are using AI to build complete systems from scratch, even when mature solutions already exist that solve most of the problem. Instead of leveraging existing platforms, they use AI to produce large amounts of new code.

The problem is not that AI writes code. The problem is what kind of code we are choosing to write. The fundamental question is no longer whether AI can do it, but whether it is truly worth doing.

A principle older than AI

Avoiding unnecessary code has always been one of the core principles of software engineering. From its very beginnings, the discipline has sought mechanisms to reuse proven solutions.

First came reusable functions. Then libraries appeared, allowing complete solutions to common problems to be encapsulated. Later came frameworks, which provided complete structures for developing applications. Finally, full platforms emerged that already include much of the infrastructure needed to run complex systems.

Each step in this evolution had a clear objective: solve a problem once and reuse the solution as many times as possible. This principle remains valid today, even in the age of artificial intelligence.

The 80/20 reality in enterprise software

When you analyze the architecture of many enterprise systems, a recurring pattern appears: most of the software does not actually belong to the specific business domain.

In practice, a large portion of any enterprise system consists of common infrastructure. This includes user management, permission systems, data models, reports, administrative interfaces, APIs, notification systems, automated processes, and many other technical pieces that appear in nearly every system.

In many projects, an approximate ratio can be observed: around 80% of the system corresponds to common infrastructure and only about 20% belongs to business-specific logic.

This fact has an important consequence. When a team decides to build everything from scratch, they are typically reimplementing that 80% of infrastructure that has already been solved many times in other systems. In that process, errors reappear that other platforms solved years ago.

The illusion of speed

Artificial intelligence tools can generate code at great speed, and this produces an initial sense of efficiency. Many teams perceive that building complete systems has become easier because code generation is no longer a significant obstacle.

However, writing speed does not eliminate system complexity. If a project needs thousands of lines of infrastructure, those lines will still exist even if they were generated automatically. Each one of them will still need maintenance, testing, and evolution.

For this reason, initial speed can create a dangerous illusion. A system can grow quickly during its early phases, but maintenance costs begin to appear when the system enters production and must be sustained for years.

Building with bricks or with prefabricated components

A useful analogy for understanding this situation comes from the world of construction.

One way to build a house is to lay each brick individually. With enough automation, a robot can perform this task quickly. However, the robot still has to place every single brick in the structure.

Something similar happens when complete systems are built using only low-level frameworks. Even though AI can generate the code quickly, the team still has to define and integrate every piece of infrastructure.

There is another way to build: using prefabricated components. In this case, instead of assembling thousands of individual bricks, you use complete walls that are already designed, tested, and optimized to fit together.

In software, something similar happens when mature platforms are used. Systems like Odoo, PrestaShop, or Drupal provide a large amount of infrastructure already solved. On that foundation, the team can focus on building the parts that truly differentiate the system.

Using AI at the right level

Artificial intelligence should not replace engineering discipline. Its true potential appears when it is used at the right level of abstraction.

Instead of generating complete systems from scratch, AI can be used to create extensions on top of existing platforms. It can generate modules, integrations, workflows, or specific adaptations for a particular domain.

For example, instead of developing a complete enterprise system from scratch, a team could use AI to generate specific modules on a stable platform like Odoo. This way, the common infrastructure remains solid and tested, while AI accelerates the creation of the business-specific logic.

This approach does not reduce innovation. On the contrary, it allows creative effort to be concentrated exactly where it adds the most value.

Learning new tools is easier than ever

Another frequent argument for avoiding existing platforms is familiarity. Many teams prefer to work only with technologies they already know.

However, this situation has changed significantly. Today documentation is abundant, countless learning resources exist, and AI tools themselves can help quickly understand new frameworks or platforms.

Learning a new tool may require a few days of adaptation, but that investment is usually much smaller than the time needed to maintain infrastructure built from scratch for years.

For this reason, the most important technical decision should not be based on team familiarity, but on how well the tool fits the problem.

The refactor that never comes

In many projects, a recurring promise appears: the idea that certain technical problems will be fixed later through refactoring.

Experience shows that this rarely happens. Once the system enters production, priorities change. New features arise, business demands appear, and users begin depending on the existing system.

In that context, technical debt accumulates and structural improvements are postponed indefinitely. For this reason, choosing a solid technological foundation from the start is usually a much more important decision than it seems.

Conclusion

Software engineering always involves making trade-off decisions between speed, control, complexity, and maintainability. Artificial intelligence introduces a powerful tool, but it does not change the fundamental principles of the discipline.

The ability to generate code quickly does not eliminate the need for architecture. In fact, it makes it even more important to carefully decide which parts of the system should be built and which should be reused.

Ultimately, engineering maturity is not about writing more code, but about knowing what code does not need to be written.

Artificial intelligence can help us produce enormous amounts of software. But true progress happens when we use it to build better systems, not simply bigger ones.

TOON vs JSON tabular, A technical review beyond the initial hype

This article explores TOON with a calm and objective view. The goal is to understand where TOON brings real value and where a simple tabular form of JSON or YAML can provide the same result without the need for a new format.

The motivation comes from a public discussion in the TOON community and from many parallel debates in other technical spaces. This is not an attack on TOON. It is simply an attempt to reach clarity.

It is important to note that TOON belongs to the category of prompt shorthand formats, not data serialization formats. Unlike JSON, Protocol Buffers, or MessagePack—which are designed for data exchange, storage, and network transport—TOON is specifically crafted to compact data within language model prompts. This distinction is critical: TOON does not compete with JSON as a general purpose standard, but rather occupies a narrow niche focused on reducing token usage in constrained conversational contexts.

Executive summary: TOON offers a novel syntax but no measurable technical advantage over JSON or YAML tabular conventions, which already eliminate repeated keys while remaining within established standards with mature tooling. Until reproducible benchmarks demonstrate otherwise, tabular JSON and YAML remain the safer, more interoperable choice.

What TOON tries to solve

TOON presents itself as a compact format that is friendly for language models. It reduces repeated keys, uses indentation for structure, and adds a marker N to declare the size of rows or lists.

Example from the official documentation:

users[3]{id,name,role}:
  1,Alice,admin
  2,Bob,user
  3,Carol,user

The idea is to remove repeated keys and reduce the amount of text needed to describe data rows.

It is important to note that TOON optimizes the syntax surface, not the structural semantics. The format does not enable new expressive capabilities or data relationships that JSON cannot represent. It simply changes how information is written—trading standard punctuation for custom markers and indentation rules. This means TOON is a notational variation, not a semantic innovation.

Technical foundations

Before comparing formats, it is useful to understand three key concepts:

Compact representation: The practice of removing redundant information from data structures. In tabular data, the most obvious redundancy is the repetition of field names across every row.

Repeated-key elimination: A technique where field names appear once (typically in a header) and subsequent rows contain only values. This approach is common in CSV, database query results, and spreadsheet exports.

The role of tokenization in LLMs: Language models do not process text character by character. Instead, they break input into tokens—units that can be whole words, parts of words, or symbols. The relationship between character count and token count is non-linear and depends on patterns the tokenizer has seen during training. Removing a bracket may not save a token if that bracket is part of a common sequence. Adding a rare symbol may cost more tokens than a familiar multi-character sequence. This means that visual compactness does not guarantee token efficiency.

Contextual overhead: TOON introduces a hidden cost that is often overlooked. Because the format is not part of the standard training corpus that language models learn from, every use of TOON requires additional prompt tokens to explain the syntax, provide examples, and clarify parsing rules. JSON, by contrast, is ubiquitous in training data—models have seen millions of JSON documents and can parse them with no instruction. This means that even if TOON saves a few tokens in the data itself, those savings may be offset or erased by the tokens spent teaching the model how to read TOON.

These concepts form the technical foundation for evaluating any format that claims to optimize data representation for language models.

JSON tabular

The same idea with no new syntax. A very simple approach uses JSON in tabular form. The first row is the header and the next rows are the data. It removes repeated keys but stays inside the JSON standard.

Example:

{
  "users": [
    ["id", "name", "role"],
    [1, "Alice", "admin"],
    [2, "Bob", "user"]
  ]
}

This representation:

  • avoids repeated keys,
  • remains one hundred percent standard JSON,
  • is easy to read for any library,
  • introduces no new rules and no new parser, and
  • provides a clear structure for models when the first row is interpreted as the header.

Tabular JSON is particularly effective for LLMs because it preserves JSON's hierarchical structure and type safety while eliminating textual redundancy, allowing models to navigate, transform, and validate data with fewer tokens and no new syntax.

It is important to emphasize that JSON tabular is a convention, not a new format. It relies entirely on standard JSON syntax and semantics. Any JSON parser can read it without modification. Any JSON schema validator, linter, or transformation tool works immediately. This full compatibility with the existing JSON ecosystem is a significant technical advantage: there is no need to build, maintain, or explain custom tooling.

YAML tabular

Even more compact. YAML allows a clean tabular form. This is compact, familiar for many users, and needs no extra rules.

users:
  - [id, name, role]
  - [1, Alice, admin]
  - [2, Bob, user]

Comparative analysis

A direct technical comparison across six key dimensions reveals the following:

Standardization TOON is an experimental format with no formal specification. JSON tabular relies on the full JSON standard (RFC 8259), and YAML tabular on the YAML 1.2 specification. Both established formats benefit from formal governance and industry consensus.

Parser requirement TOON requires a custom parser. JSON tabular works with any JSON parser, and YAML tabular with any YAML parser. This means zero integration friction for the established formats.

Compactness TOON is slightly more compact in visual terms. JSON tabular is very compact, removing repeated keys while staying within standard syntax. YAML tabular is the most compact due to minimal punctuation.

Safety TOON's N marker can catch errors but also introduces inconsistency risk when the marker diverges from actual data. JSON tabular and YAML tabular both support standard validation mechanisms (JSON Schema and YAML schema) without embedding counts in the data itself.

Readability by LLMs TOON requires format explanation in every prompt. JSON tabular and YAML tabular are widely seen during model training and immediately recognized without instruction.

Real world tooling TOON has limited, experimental tooling. JSON tabular benefits from a massive ecosystem including jq, validators, IDEs, and debuggers. YAML tabular has a strong ecosystem with yq, validators, and IDE support.

This comparison shows that for uniform tabular data, the established conventions offer clear advantages in tooling, standardization, and model familiarity, while TOON's benefits remain theoretical without supporting benchmarks.

A critical absence: This analysis does not include empirical performance metrics—token counts, parsing accuracy, regeneration fidelity—because no such public data exists. Until TOON is tested against JSON tabular and YAML tabular in reproducible conditions, claims of superiority remain unsubstantiated. In methodological terms, the burden of proof rests on the proponents of the new format.

The original technical question was simple

These questions do not require theory, speculation, or subjective judgment. They are directly measurable through straightforward experiments: encode identical datasets in each format, count tokens with real tokenizers, test model accuracy, and compare results. Such experiments have not been presented.

  1. When does TOON offer a real advantage over JSON tabular for uniform data?
  2. Is the value of the N marker real or only a source of extra complexity?
  3. Are there benchmarks that compare TOON with JSON tabular in terms of tokens and data accuracy?

These questions need careful answers.

What the TOON maintainers responded — and what they did not

The discussion that motivated this article began in TOON Discussion #138, where I raised these same questions directly to the maintainers: https://github.com/toon-format/toon/discussions/138

Their reply was concise, friendly, and transparent. This is the relevant portion, quoted verbatim:

"If you're happy to stay in JSON and your data is flat-ish, uniform, not huge… your header-row JSON is totally reasonable! The JSON-with-header pattern is already close to TOON. The gaps are: TOON still removes more syntax (no per-row [], fewer quotes, CSV-like rows). [N]{fields} are normative guardrails: decoders must enforce row count/width + delimiter. Same rules recurse for nested arrays-of-objects. If [N] is wrong, that's a feature in strict mode: it fails validation instead of silently accepting truncated data."
— TOON maintainers, Discussion #138

Their response was polite and clear—but it did not address the core technical questions raised in this article:

  • They confirmed that tabular JSON is "totally reasonable" for flat and uniform data.
  • They acknowledged that JSON-with-header is already close to TOON.
  • They listed differences (syntax removal and the N marker) but did not provide evidence that these differences yield advantages for LLM performance.
  • They did not present token measurements.
  • They did not provide accuracy benchmarks.
  • They did not compare regeneration fidelity.
  • They did not evaluate tabular JSON directly in any experiment.

In other words, the reply explains what TOON does, but not whether TOON performs better than established tabular conventions under LLM tokenization, accuracy, or reasoning workloads.

As a result, the original questions remain unanswered, and claims of superiority for TOON over JSON/YAML tabular remain unverified.

Technical analysis

Token savings

The token savings of TOON over JSON tabular are often very small. Removing quotes or braces does not always reduce tokens because language models use complex token rules that do not follow characters one by one. The following examples illustrate why visual compression does not guarantee token savings:

  • The sequence {"id": might tokenize as [{, ", id, ", :] — five tokens.
  • A rare marker like ⊗ might tokenize as [<0xE2>, <0x8A>, <0x97>] — three tokens for one character.
  • The string users[3] might tokenize as [users, [, 3, ]] — four tokens, the same as "users": which is [", users, ", :].

This means:

  • sometimes a strange symbol costs more tokens than normal text
  • sometimes removing braces does not change token count
  • the explanation of the TOON format itself also consumes tokens

There is no strong evidence that TOON always saves tokens in practice. Visual reduction does not equal token reduction.

Therefore, TOON offers aesthetic compactness, not guaranteed token efficiency.

Value and risk of N

N is a form of internal validation. It can help detect errors in strict controlled flows. But it also creates a second truth that can become incorrect.

If N is wrong, the format breaks. This may be useful in tightly controlled scenarios, but it also becomes a systematic source of fragility. JSON tabular does not have this risk because the shape of the data is clear without markers.

N introduces a dual source of truth: the marker must stay synchronized with actual row count, creating a failure point that JSON tabular avoids through self-evident structure. JSON Schema and similar validators can enforce constraints externally without embedding counts in data.

A concrete failure scenario illustrates this risk. Suppose a model generates:

users[6]{id,name,role}:
  1,Alice,admin
  2,Bob,user
  3,Carol,user
  4,Dave,moderator
  5,Eve,guest
  6,Frank,admin
  7,Grace,user

The marker declares six rows, but seven are present. A strict TOON parser rejects this entirely despite valid data. JSON tabular avoids this: array length is self-evident, and external validation introduces no fragility.

TOON is a prompt only format, not a data format

TOON is not for network transport

TOON is not designed for network transmission or storage. It is not a standard and has no real ecosystem. It only exists to feed prompts to language models. For all real world systems, JSON, CSV, Protobuf or MessagePack are far better choices.

TOON cannot be used safely in systems requiring round trip fidelity—that is, workflows where data travels from an API to an LLM and back to a client. Because TOON is not a standard, any deviation in parsing, regeneration, or formatting can be fatal for the pipeline. A model that returns malformed TOON breaks the entire flow. JSON, by contrast, can be validated, repaired, and transformed with robust tooling at every step.

What the wider technical community says

These observations come from practitioners across machine learning, backend engineering, data engineering, and prompt engineering—disciplines with direct experience in token optimization, model behavior, and production system constraints.

In different platforms there are repeated points:

  • TOON may save tokens in some cases but not in many others
  • token savings depend on the exact words and do not follow character count
  • a simple tabular form of JSON or YAML often gives the same benefit
  • new formats add mental cost and bring no clear long term value
  • the benefits of TOON are sometimes smaller than the cost of teaching the model the format
  • every new syntax requires mental and instructional overhead that JSON and YAML avoid due to universal familiarity—developers, models, and tooling already understand JSON; introducing TOON means documentation, examples, error handling, and cognitive load with no guaranteed payoff

These points match the analysis done here.

Hype and common misunderstandings around TOON

Many public posts describe TOON as a fresh standard or even as a replacement for JSON. TOON circulates heavily on social platforms because it promises savings in cost and performance, two themes that spread faster than verified evidence. When a format claims to reduce API expenses or improve model reasoning, that message travels quickly—often before rigorous testing can validate or refute the claims. This creates a cycle where enthusiasm precedes measurement, driven by both economic incentives (token costs translate to API expenses) and psychological incentives (novelty and early adopter status). Together, these forces create disproportionate expectations that outpace empirical validation.

Popular claims and the corresponding technical reality

1. "TOON is already a standard." In reality, a true standard requires broad industry adoption, mature tooling, sustained support, and formal governance bodies. TOON is still experimental and has no production deployments.

_How to act_: Treat TOON as a community experiment, not as the foundation for critical systems.

2. "TOON will replace JSON." JSON dominates transport, storage, APIs, configuration files, databases, and logging. TOON only attempts to compact data inside LLM prompts; it does not compete in any other domain.

_How to act_: Each format solves a different problem. Do not plan infrastructure migrations toward TOON.

3. "Models struggle with JSON." Current language models read, repair, and complete JSON—including header based tables—with high accuracy. No evidence shows that TOON is easier.

_How to act_: JSON remains a safe and mature choice.

4. "Fewer characters equals fewer tokens." Tokenizers operate on learned patterns, not character counts. Rare symbols can cost more tokens than common JSON structures, and teaching new syntax consumes tokens. See Technical analysis section for details.

_How to act_: Always measure with real token counts.

5. "We need a new format for compact tables." Tabular JSON and YAML already remove repeated keys while remaining completely within established standards. Validation can be performed externally without introducing custom syntax.

_How to act_: Before adopting TOON, verify whether a standard tabular variant already satisfies the need with less risk and more interoperability.

6. "TOON improves model reasoning." No published study demonstrates improved reasoning, coherence, logical accuracy, or transformation fidelity using TOON compared to JSON tabular. The claim assumes that compactness enhances comprehension, but models are trained on verbose natural language and structured JSON—not minimalist notations.

_How to act_: Treat the claim as unverified until benchmarked in controlled conditions with multiple models and diverse reasoning tasks.

Conclusion

TOON optimizes aesthetics; tabular JSON optimizes standards compliance. The former prioritizes visual compactness and novel syntax; the latter prioritizes interoperability, tooling maturity, and zero onboarding cost. _Elegance without interoperability is fragile; interoperability without elegance is robust._ Systems built on standards survive because they integrate seamlessly and benefit from collective tooling investment. Custom notations survive only within the boundaries where they are understood.

TOON serves a narrow prompt compaction niche where inline validation and strict row counts justify custom syntax. For uniform datasets, JSON tabular and YAML tabular provide compact encodings within mature standards and should remain the default.

Innovation is healthy, but the burden of proof rests on those proposing new formats. TOON has not yet demonstrated measurable benefits through reproducible benchmarks. Until that evidence exists, treating TOON as an experiment rather than a standard keeps expectations aligned with reality.

Moving forward: What future debates should include

To move beyond speculation and reach technical clarity, any future discussion or evaluation of TOON—or any similar format—should include:

  • Reproducible token benchmarks: Measure token counts for identical datasets encoded in TOON, JSON tabular, and YAML tabular using the actual tokenizers of production LLMs (e.g., GPT-4, Claude, Llama). Publish the raw data and methodology.
  • Model accuracy comparisons: Test how accurately models parse, transform, and regenerate data in each format. Track error rates, hallucinations, and structural failures across multiple prompts and models.
  • Real LLM round-trip tests: Execute full cycles: provide data in a format, ask the model to reason about it, request regeneration in the same format, then validate the output programmatically. Measure success rates and token costs at each step.
  • Schema behavior under recursion and nested data: Test TOON, JSON tabular, and YAML tabular with deeply hierarchical structures such as arrays within objects within arrays, recursive references, and mixed type collections. Flat tabular data is only one use case; many real world datasets require nesting, and it is unclear how TOON handles complexity beyond uniform rows.

Without these concrete measurements, debates remain trapped in speculation. With them, the technical community can make informed decisions based on evidence rather than aesthetics or hope.

Software Engineering Principles

  • The Robustness Principle: Postel, J. (1980). _DOD Standard Transmission Control Protocol_. RFC 761. "Be conservative in what you send, be liberal in what you accept" - relevant to standard format adoption.
